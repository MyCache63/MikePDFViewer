## 1. Goal

Let MikePDFViewer open and view `.eml` files (saved emails — Outlook/Gmail/Apple Mail format) the same way it opens PDFs. The app should:

- Show the email's headers (From, To, Subject, Date)
- Show the email body (HTML or plain text)
- Show any inline images
- List attachments and let the user save or view them
- Reuse as much of the existing PDF viewing pipeline as possible (toolbar, sidebar, search, print, annotations)

## 2. The Sample File

I looked at `/Users/michaelashe/Documents/KoreClients/Humana/Humana Patient Experience Survey RFP.eml`:

- 70 KB, plain text MIME format (RFC 822)
- Headers include the usual: `From`, `To`, `Subject`, `Date`, `Message-ID`, `References`, `In-Reply-To`
- Generated by Microsoft Outlook (Office 365)
- Contains DKIM signatures and Microsoft anti-spam headers (a lot of noise we'll filter out)
- The body itself starts after the blank line that follows the headers

This is a typical corporate email. Real-world EML files are messy — multiple encodings, nested multipart sections, base64-encoded attachments, inline images referenced by `cid:` URLs.

## 3. What's Out There — Library Survey

I searched GitHub for Swift EML parsing libraries. Here's what's available:

| Library | License | SwiftPM | Active | Notes |
|---------|---------|---------|--------|-------|
| **MimeParser** (miximka) | MIT | Yes | Last release Apr 2022, stable | Pure Swift, handles RFC 822/2045/2046, multipart, attachments. Best fit. |
| MimeEmailParser (igorrendulic) | MIT | Yes | Older, less maintained | Focused on validation more than parsing |
| AddressParser (onevcat) | MIT | Yes | Stable | Address parsing only — would need to combine with another library |
| Hedwig | MIT | Yes | Less active | Full SMTP client, way more than we need |

**Recommendation: Use MimeParser.**

- It's MIT-licensed (no licensing concerns)
- It's pure Swift, no Objective-C bridging
- It's stable and small (~68 commits, focused scope)
- It handles the multipart structure we need
- SwiftPM means we add it via Xcode "Add Package Dependency" — no manual file copying

GitHub: https://github.com/miximka/MimeParser

If MimeParser turns out to have gaps (e.g., quoted-printable decoding for non-UTF8 bodies), we can supplement with our own utility code. The library is small enough that we could fork it if needed.

## 4. Architecture — Three Approaches

There are three ways we could integrate this. I recommend Option A.

### Option A — Convert EML to PDF on open (RECOMMENDED)

When the user opens a `.eml` file, we:

1. Parse the EML with MimeParser
2. Build an HTML page with the headers at the top and the email body below
3. Render that HTML to a PDF using `WKWebView`'s built-in print-to-PDF
4. Open the resulting PDF in the existing PDFKit viewer
5. Show attachments in a side panel or footer, each downloadable

**Pros:**
- Reuses ALL existing features automatically: annotations, search, print, save, watermark, signatures, comparison, OCR, export-as-images
- One consistent UX — emails look like documents
- The "saved" version of an email is a real PDF the user can share/archive
- No duplicate viewer code to maintain

**Cons:**
- Conversion happens on open (small lag — likely <1 second for typical email)
- Slightly lossy — HTML→PDF can shift layout (acceptable for viewing)
- Attachments need a separate UI (won't be embedded in the PDF body)

### Option B — Native EML view alongside PDF view

Add a separate `EMLView.swift` that renders the email natively using SwiftUI + a small `WKWebView` for the HTML body. Switch between PDF and EML modes based on file extension.

**Pros:**
- Pixel-perfect HTML rendering
- Faster open (no conversion step)

**Cons:**
- Two viewers to maintain forever
- Loses search/annotations/print/export across emails (would need to be re-implemented for the EML view, or just disabled)
- Inconsistent UX — toolbar buttons would dim or behave differently for emails

### Option C — Hybrid (Default to PDF conversion, but offer "View Original")

Like Option A, but add a menu item "View Original Email" that pops open the raw EML in a separate window for cases where the PDF version looks bad.

**Pros:**
- Best of both worlds
- Failsafe if conversion looks weird

**Cons:**
- More code than A
- Most users will never use it

**My recommendation: Start with Option A. If it works well, ship it. If a particular email looks bad, we can add Option C's "View Original" escape hatch later.**

## 5. Implementation Plan (Option A)

### Phase 1 — EML parsing and PDF conversion (2–3 days)

**New files:**

| File | Purpose |
|------|---------|
| `EMLService.swift` | Parses .eml, returns headers + body HTML + attachments list |
| `EMLToPDFConverter.swift` | Takes parsed EML, builds HTML page, renders to PDF via WKWebView |
| `EMLAttachment.swift` | Lightweight struct: filename, MIME type, data, size |

**Existing files to modify:**

| File | Change |
|------|--------|
| `MikePDFViewerApp.swift` | Register `.eml` as a supported document type. Add to `Info.plist` `CFBundleDocumentTypes`. |
| `Info.plist` | Add UTType for `eml` (com.apple.mail-message or public.email-message). |
| `ContentView.swift` | Detect `.eml` in `loadDocument`. Route through EMLToPDFConverter before passing to PDFKit. |
| `RecentFilesManager.swift` | Allow `.eml` in recent files. |

**Parsing flow:**

```
URL (.eml) → Data → MimeParser.parse(string)
                            ↓
                    Mime tree (headers + parts)
                            ↓
        ┌───────────────────┼───────────────────┐
        ↓                   ↓                   ↓
   Header struct     Body HTML/text      Attachments[]
        │                   │                   │
        └─────────→ HTML page builder ←─────────┘
                            ↓
                    WKWebView.printPageRenderer
                            ↓
                       PDFDocument
                            ↓
                  Existing PDFKit viewer
```

**Header rendering (HTML):**

Show only the user-meaningful headers, not the routing junk:

- From, To, Cc, Bcc, Subject, Date
- Maybe Reply-To if different from From
- Skip: DKIM, ARC, Received, Message-ID, X-* headers (collapse into "Show technical headers" disclosure if needed)

**Body rendering:**

- If `multipart/alternative`: prefer `text/html`, fall back to `text/plain`
- If only `text/plain`: wrap in `<pre>` tag with monospace font
- If `multipart/mixed`: pull attachments out of the tree, render the rest as the body
- Inline images (`cid:` URLs): rewrite to data URLs so they render in the PDF

**Attachments:**

- List below the email body in the rendered PDF (filename, size, type)
- Also exposed in a sidebar "Attachments" section (UI in Phase 2)

### Phase 2 — Attachments UI (1–2 days)

**New file:**

| File | Purpose |
|------|---------|
| `AttachmentsSidebar.swift` | Side panel showing attachment list. Click to save or open. |

**Existing files to modify:**

| File | Change |
|------|--------|
| `ContentView.swift` | When viewing an EML-derived PDF, show attachments panel (right side or below thumbnails). |
| `PDFKitView.swift` | Carry the original EML attachments alongside the PDF document so they're available to the UI. |

**UX:**

- Right side panel (or expandable footer) shows: attachment name, type icon, size
- "Save" button per attachment → writes to user-chosen location
- "Open" button → for attachments that are PDFs, open in a new MikePDFViewer window. For other types, hand off to the OS (`NSWorkspace.shared.open`)
- If an attachment is itself an `.eml` (forwarded email), recurse

### Phase 3 — Polish and edge cases (1 day)

- Encrypted/signed emails (S/MIME): show a "this email is encrypted" notice rather than failing
- Calendar invites (`text/calendar`): show as attachment, optionally add a "View in Calendar" button
- Empty body: handle gracefully
- Non-UTF8 encodings (Latin-1, Windows-1252, etc.): MimeParser may need a wrapper to handle charset detection
- Very large attachments (>50 MB): don't load into memory eagerly — keep a reference to the original file
- HTML emails with tracking pixels / external images: BLOCK external loads in WKWebView (privacy + offline reliability)

- Test with an Outlook EML that has a PDF attachment

## 7. Risks

- **MimeParser gaps:** If the library can't handle some real-world edge case (weird charset, deeply nested multipart), we may need to write custom parsing or fork the library. Low probability, but worth noting.
- **WKWebView print-to-PDF quality:** HTML emails sometimes have inline CSS that doesn't render well at print size. We may need to inject a stylesheet that overrides the email's CSS. Manageable.
- **macOS sandbox / file access:** Opening attachments will need user-granted file access. The existing `MikePDFViewer.entitlements` already has user-selected file access — should "just work."
